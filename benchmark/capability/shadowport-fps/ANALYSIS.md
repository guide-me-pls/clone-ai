# Shadowport FPS benchmark — baseline analysis (2026-11-18)

**English** · [简体中文](ANALYSIS.zh-CN.md)

This is the first measured run of the [Shadowport one-query FPS benchmark](README.md).
It asks whether one user message, from a clean workspace, can produce a playable
tactical FPS that the agent verifies itself. The answer here is **yes, with a
caveat**: the second clean run produced an eight-enemy FPS with relays,
extraction and a debrief, used the browser tools without a single tool error,
and passed the independent checker 17/17. The terminal Run status is
`waiting_review`, not `completed`, because the plan's acceptance criteria are
prose rather than machine-readable file/test contracts.

## 3. What the worker actually did

The Main Agent queued a single self-contained step with `propose_work_plan`
(3 model calls), so the chat turn returned in 17.9 s. The worker read the
workspace, wrote `game.js` and `index.html`, then used the browser tools to:

- open `http://127.0.0.1:8138/` and wait for the first frame;
- read the console after changes;
- evaluate `window.__game` state, move the player, fire at an enemy, cut the
  three relays and reach extraction;
- save menu/game/relay/debrief screenshots.

The artifact is a classic-script Three.js page: rainy container port, first
person, pointer lock, ADS/stance, hitscan rifle with head detection, enemies
with patrol/alert/cover/reinforcement behavior, a three-relay objective, a
debrief, and a minimal local HUD. It is not a AAA game; it is a playable
one-query prototype. The single-file build
`eval-runs/2026-11-18-shadowport-clean2/dist/shadowport.html` (705 KB) opens from
`file://` with zero external requests and passes start/move/relay/extraction in
the same browser check.

## 4. What the baseline says about the harness

- **Queueing matters.** The same class of build previously blocked the Main
  Agent for ~50 minutes inside `dispatch_task`; a queued plan returned in 17.9 s
  and ran the worker separately.
- **The last-round budget notice matters.** A 60-round build that produced a
  complete game but never answered failed; with two rounds reserved it stops and
  reports.
- **The browser tools matter.** The worker's own console/state/screenshot loop is
  what separates this from blind file generation. The Playwright MCP subset had
  no tool errors in the self-verified run.
- **A preview port mismatch is a harness failure, not a game failure.** clean1's
  game passed 17/17 externally while its worker checked a stale 8137; the
  `setup.mjs` port substitution exists to prevent exactly that.

## 5. Limitations

- One run per configuration; no statistical repeat or model comparison yet.
- The checker drives the public hook, not a human's feel for gunplay, audio or
  fun. Those still need an owner playtest.
- `waiting_review` is the terminal status because the plan's criteria are prose;
  a machine-readable test contract would let the Kernel complete the run.
- Windows GPUs and non-Chrome browsers are unmeasured.
- The cost is real: 744k tokens and ~5.5 minutes for the self-verified run.
- The benchmark measures a tactical FPS prototype, not parity with a commercial
  title.

node --experimental-strip-types scripts/install-browser-mcp.mjs --workspace /tmp/shadowport-clean --clone-home /tmp/shadowport-home --port 8138
CLONE_AI_MAIN_EFFORT=medium node --experimental-strip-types eval-runs/2026-11-17-browser-mcp/run.mjs /tmp/shadowport-clean /tmp/shadowport-home benchmark/capability/shadowport-fps/prompt.md
