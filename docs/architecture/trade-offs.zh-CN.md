# 架构取舍

[English](trade-offs.md) · **简体中文**

只有把理由写下来，一个决定才算真正稳定。每条记录都说明决定了什么、依据是什么，以及在
什么条件下后来者应当推翻它。

## 2026-11-05 — 提示词溯源 = 内容寻址文件 + 一条 Journal 事件

**决定。** 每个主 Agent 回合记录 charter 版本、编译后的情境简报、实际注册的工具表、
模型 id 与推理强度。完整材料写入 `<clone home>/prompt-snapshots/<materialHash>.json`；
Journal 追加一条 `main_agent.prompt_snapshot` 事件，携带各项哈希、定位符，以及桌面回合
的 turn id。

**依据。** 改动之前，Journal 能说明 Agent 做了什么、召回什么，却说不清它被告知了什么：
`MAIN_AGENT_CHARTER` 是常量，情境简报只存在于单个会话的内存里，工具表只存在于 Pi 会话
内部。因此失败的一轮无法归因到某一版提示词，两次"改进"也无法与基线比较。Journal 本来
就是 append-only 的真相（[`state-projector.ts`](../../src/state/state-projector.ts) 从
它重建状态），所以溯源应当放在这里，而不是另开一份日志。

**推翻条件。** 如果 Journal 不再是回合级遥测的合适归宿（例如保留策略要求 Run 与回合按
不同周期过期），就把事件迁移到以同一个 `materialHash` 为键的专用存储；哈希方案与文件
布局不依赖 Journal。

## 2026-11-05 — 工具溯源在注册时捕获，而不是维护一份清单

**决定。** `createKernelToolsExtension` 在注册每个工具的同一时刻通过 `onRegister` 回调
上报它。哈希覆盖模型真正收到的名称、描述与参数结构。

**依据。** 手工维护的工具名清单是第二个真相来源，第一次重命名或新增工具时就会悄悄漂移
——而这正是溯源要暴露的不可见变更。回调看到的是被注册的对象本身，因此不可能与会话不一致。

**推翻条件。** 如果工具可以在 `createKernelToolsExtension` 之外注册（第二个扩展工厂，
或 MCP 托管的工具），注册入口就不再覆盖完整工具表；届时快照必须从会话读取工具列表，
而不是依赖回调。

## 2026-11-05 — 回归门禁离线、逐用例、只衡量行为

**决定。** `npm run gate` 对 held-out 夹具重新运行证据验证与权限策略，用所有者标注
校准审计记录，并把每个用例与记录的基线比较。它不调用模型，是 CI 的必需步骤。

**依据。** 本仓库的保证位于模型周围的规则：完成来自证据，权限来自 Scope，所有者判定
来自 `audit.labeled`。这些层是确定性的，因此零成本门禁可以在每次提交时覆盖它们。
依赖 Provider 的评估，恰恰会在 CI 承压时被跳过。

**推翻条件。** 如果录制的轨迹 cassette 能在无网络环境下回放，就在确定性套件旁边增加
轨迹套件。逐用例基线对判断层始终有效。

## 2026-11-05 — 判定变化即使是改进也会让门禁失败

**决定。** `baseline.json` 记录每个用例当前的结果；任何差异——通过变失败或失败变通过
——都会失败，直到在同一次变更中运行 `--write-baseline`。

**依据。** 未经 diff 审查就到达的改进，与一个恰好在夹具集上看起来更好的回退无法区分。
强制更新基线，使审查者必须看到行为差异及其理由。

**推翻条件。** 如果基线变动开始主导审查成本，就按套件拆分，或为每个用例增加明确的
意图说明；不要改成静默自动更新。
