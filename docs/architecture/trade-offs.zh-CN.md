# 架构取舍

[English](trade-offs.md) · **简体中文**

只有把理由写下来，一个决定才算真正稳定。每条记录都说明决定了什么、依据是什么，以及在
什么条件下后来者应当推翻它。

## 2026-11-06 — 设置页以 Worker 为语言，并让派发可见

**决定。** 从 Agent 设置页移除历史的"本地 Provider"列表，把它的信息（是否安装、命令、执行边界、安装操作）并入每个 Worker 行。设置导航改为真正的 tab 列表——`role=tablist/tab/tabpanel`、`aria-selected`、方向键与 Home/End、焦点跟随选择、逐面板记忆滚动位置、120ms 淡入/位移并尊重 `prefers-reduced-motion`。在 Run 审计详情中增加「Worker 派发」块：逐步显示选中的 Worker、其 Provider、路由来源（显式/规则/记忆/描述）与理由，数据来自 Journal 的 `dispatch.decided` 事件。

**被否决的备选。**（a）保留 Provider 列表并改名"运行时"——同一台机器的两份列表，所有者仍要自行翻译。（b）把 Provider 控件移到独立页面——把安装与执行边界的事实从它们所治理的 Worker 身边移开。（c）只在原始轨迹里显示派发——它确实在那里，但"这一步为什么给了那个 Worker"是一等公民问题，不是调试细节。

**证据。** 所有者反馈设置交互生硬、Provider 列表是历史遗留；派发决定本就记录了 `selectedAgentId`、`providerId`、`source` 与 `reason`（`src/main-agent/dispatch-recorder.ts`），新块不引入新数据。确定性检查：`test/ui-structure.test.ts` 断言不再有 `provider-registry` 区块、设置标签具备 tab 语义、审计页渲染派发块。

**成本与推翻条件。** Worker 行会多一行元数据；移除 Provider 区块后，没有任何 Worker 绑定的 Provider 不再出现在 UI 中。若所有者需要在绑定任何 Worker 之前管理某个 Provider，或 tab 语义在打包的 WebKit 中出问题，应推翻此决定。

## 2026-11-05 — Agent 自己运行对抗性测试与修复回路

**决定。** 增加一套确定性、离线的对抗性测试（注入包裹、审批重放/过期/转发、受保护路径与符号链接逃逸、Worker 环境中的工具凭据、secret 记忆召回、轨迹脱敏、限流），并增加一个自检回路：每一轮写入 Journal；探针变红时把失败导出为轨迹，交给既有的带闸门修复通道。每轮运行对抗套件、`npm run gate`，可选 `npm test`；修复仍只产出草稿 PR，合并权在所有者。

**被否决的备选。**（a）以模型驱动的红队为主回路——不确定、每轮消耗 token、跨轮无法比较；留作后续层。（b）让回路直接改代码——违反既有修复闸门，也让"是否变好"无法回答。（c）另起测试运行器——仓库已有 `npm run gate` 与 `node --test`，第二套会漂移。

**证据。** 每个探针都对应代码里已经存在的边界，并有单测或既往事故：转发 WhatsApp 内容（`forwarded` + `<untrusted_data>`）、审批码（一次性、哈希、TTL）、`forbiddenRoots`、`assertWorkerEnvName`、secret 记忆排除、`digestEvents`。套件把这些变成同一个可测量、可记录的信号，而不是散落的假设。确定性探针在本次修订上通过；回路的修复分支用 `--dry-run` 验证。

**成本与推翻条件。** 每轮只耗 CPU，增加一条 Journal 事件和一个报告文件；只有探针变红且传入 `--repair` 时才消耗模型 token。若套件不再能区分回归与噪声（探针无论代码如何都通过），或真实事故暴露了套件未覆盖的类别，应扩展套件而不是放宽它。

## 2026-11-05 — 所有 Agent 调用在 CLONE_HOME 之外审计

**决定。** 每次 Main Agent 调用都在 `~/.clone/audit/invocations.jsonl` 下写入共享、
追加式记录，不受调用的 `CLONE_HOME` 影响。记录包含调用者、界面、可见请求与回复、错误、
Workspace、数据目录、模型、推理强度、会话文件、Run id 与耗时。受控部署和测试可通过
`CLONE_AI_AUDIT_HOME` 移动账本。

**依据。** 自修复运行使用了临时 `CLONE_HOME`；Journal 本身正确，但桌面审计读取所有者
常规主目录，因此完全看不到。改动后，使用隔离主目录的一次真实 DeepSeek V4.1 Flash
`high` 调用出现在默认共享账本中，调用者为 `codex`，回复为 `OK`（调用 id `7cb576ee`）。

**代价和推翻条件。** 这会增加第二个存储位置，且可见回复属于敏感数据；账本会做 PII/Token
脱敏、截断，并且不包含私有推理。如果明文 JSONL 不再满足威胁模型，应迁移到加密的、
所有者作用域的存储。

## 2026-11-05 — 根级文件名需要明确的文件意图

**决定。** 继续提取带目录分隔符的普通路径，但排除 URL、代码表达式及含常量式全大写
目录段的路径。无分隔符的根级文件名必须在同一句或同一条标准中有明确文件意图词，且
扩展名属于保守白名单。否决把所有带点的词都当作文件，也否决对已有目录分隔符的路径
强制要求意图词。

**依据。** 夜间修复的轨迹中，验证器把 `fs.rename`、`os.tmpdir`、
`consumed-traces.json` 和 `REPORT_DIR/consumed-traces.json` 当成工作区必需文件，导致
假失败。源码检查显示旧提取器没有区分这些带点的文本。修改后的定向离线回归测试已通过；
更广泛的覆盖效果仍属假设。本工单未运行修改前的评估。

**代价和推翻条件。** 真正的根级交付物若同一句或标准中没有意图词，或扩展名不在白名单，
就会被漏提取。若有代表性的真实交付物表明漏检影响实际使用，应重新审视此规则，并在保留
排除项的回归用例前提下扩充意图词或白名单。

## 2026-11-05 — 规划孤儿只在保守宽限期后恢复

**决定。** 仅当规划中的 Run 没有计划、没有存活领取，且最后更新已超过 15 分钟时，
才将其标记为失败。先获取恢复领取，再以原子条件写入：如果刷新投影后 Run 发生变化，
拒绝写入。无法提供这种带条件的围栏写入的存储保持不变；执行与验证阶段的恢复不变。

**依据。** 现有恢复只扫描 `running` 和 `verifying`；规划者在生成计划前退出可能使 Run
永久停留在 `planning`。假设普通的无领取规划在 15 分钟内完成属于保守但未经测量的假设；
没有租约的活跃规划仍可能超过这个时间。立即失败或仅凭时间判定会危及新建或已领取的工作。
仅在内存中复查，则可能在写入失败前覆盖并发生成的计划或取消操作。

**推翻条件。** 如果观测到正常的无领取规划超过 15 分钟，应先改用可靠的规划者租约，
或根据实测时长调整阈值，再启用此恢复逻辑。

## 2026-11-05 — 提示词溯源 = 内容寻址文件 + 一条 Journal 事件

**决定。** 每个主 Agent 回合记录 charter 版本、编译后的情境简报、实际注册的工具表、
模型 id 与推理强度。完整材料写入 `<clone home>/prompt-snapshots/<materialHash>.json`；
Journal 追加一条 `main_agent.prompt_snapshot` 事件，携带各项哈希、定位符，以及桌面回合
的 turn id。

**依据。** 改动之前，Journal 能说明 Agent 做了什么、召回什么，却说不清它被告知了什么：
`MAIN_AGENT_CHARTER` 是常量，情境简报只存在于单个会话的内存里，工具表只存在于 Pi 会话
内部。因此失败的一轮无法归因到某一版提示词，两次"改进"也无法与基线比较。Journal 本来
就是 append-only 的真相（[`state-projector.ts`](../../src/state/state-projector.ts) 从
它重建状态），所以溯源应当放在这里，而不是另开一份日志。

**推翻条件。** 如果 Journal 不再是回合级遥测的合适归宿（例如保留策略要求 Run 与回合按
不同周期过期），就把事件迁移到以同一个 `materialHash` 为键的专用存储；哈希方案与文件
布局不依赖 Journal。

## 2026-11-05 — 工具溯源在注册时捕获，而不是维护一份清单

**决定。** `createKernelToolsExtension` 在注册每个工具的同一时刻通过 `onRegister` 回调
上报它。哈希覆盖模型真正收到的名称、描述与参数结构。

**依据。** 手工维护的工具名清单是第二个真相来源，第一次重命名或新增工具时就会悄悄漂移
——而这正是溯源要暴露的不可见变更。回调看到的是被注册的对象本身，因此不可能与会话不一致。

**推翻条件。** 如果工具可以在 `createKernelToolsExtension` 之外注册（第二个扩展工厂，
或 MCP 托管的工具），注册入口就不再覆盖完整工具表；届时快照必须从会话读取工具列表，
而不是依赖回调。

## 2026-11-05 — 回归门禁离线、逐用例、只衡量行为

**决定。** `npm run gate` 对 held-out 夹具重新运行证据验证与权限策略，用所有者标注
校准审计记录，并把每个用例与记录的基线比较。它不调用模型，是 CI 的必需步骤。

**依据。** 本仓库的保证位于模型周围的规则：完成来自证据，权限来自 Scope，所有者判定
来自 `audit.labeled`。这些层是确定性的，因此零成本门禁可以在每次提交时覆盖它们。
依赖 Provider 的评估，恰恰会在 CI 承压时被跳过。

**推翻条件。** 如果录制的轨迹 cassette 能在无网络环境下回放，就在确定性套件旁边增加
轨迹套件。逐用例基线对判断层始终有效。

## 2026-11-05 — 判定变化即使是改进也会让门禁失败

**决定。** `baseline.json` 记录每个用例当前的结果；任何差异——通过变失败或失败变通过
——都会失败，直到在同一次变更中运行 `--write-baseline`。

**依据。** 未经 diff 审查就到达的改进，与一个恰好在夹具集上看起来更好的回退无法区分。
强制更新基线，使审查者必须看到行为差异及其理由。

**推翻条件。** 如果基线变动开始主导审查成本，就按套件拆分，或为每个用例增加明确的
意图说明；不要改成静默自动更新。

## 2026-11-05 — Worker 只继承模型凭据，不继承工具凭据

**决定。** Provider 声明可以点名模型客户端需要的凭据；任何工具凭据（`GITHUB_TOKEN`、
`AWS_*`、`GOOGLE_APPLICATION_CREDENTIALS`、`*_SECRET` 等）在启动前被拒绝，错误信息指向
凭据代管。

**依据。** 带 shell 和 token 的黑盒 Worker 能做该 token 允许的一切；模型需要 API Key 才能
回答，但不需要所有者的代码托管或云凭据。检查发生在构建期、进程存在之前，因此错误声明无法
泄漏进运行中的 Worker（`test/worker-env.test.ts`）。

**代价。** 确实需要工具凭据的 Worker 不能靠继承配置，必须走代管。

**推翻条件。** 若某个可信、范围极窄的操作需要工具凭据，增加经 Kernel 授权后的按次代管注入；
不要重新开启继承。

## 2026-11-04 — 失败轨迹与修复只在有闸门的草稿 PR 通道运行

**决定。** 失败与取消的 Run 变成脱敏的自包含轨迹，包括没有错误码的隐性失败：同一步骤重试
三次以上、取消、被判“不合格”、或运行结束后十分钟内的所有者纠正。夜间修复在全新 worktree
中运行，要求回归测试在修复前被脚本验证为红，跨阶段对测试文件做哈希，禁止受保护路径进入
diff，只产出草稿 PR（或补丁文件）。它从不合并、部署、重启或修改自己的计划。

**依据。** 无人值守的代码生成是系统里风险最高的动作。每道闸门对应一种已知失效模式：在正在
服务的检出里写代码；没有复现的“修复”；模型靠重写测试让套件变绿；修复改动了审判它的规则；
以及自动合并。`scripts/nightly-rsi.mjs` 实现了全部五道，并在报告里声明合并仍由所有者决定。

**代价。** 测试加 diff 检查只能限定伤害，不能证明修复安全；PR 仍需人读。没有轨迹就不运行，
失败时保留 worktree 供检查。

**推翻条件。** 不要为通用修复放宽草稿 PR 闸门。若沙箱化运行器能对全量测试证明修复并机械
执行受保护路径规则，另一条取舍可以允许对具名路径白名单自动合并——绝不针对宽泛变更。

## 2026-11-04 — 自我评审只改配置，不改规则

**决定。** 评审读取审计摘要，最多提出四个动作，仅限 worker 或主 Agent 的模型与推理强度。
每个动作对照机器声明支持的能力校验，只在所有者点击时应用，以 `recommendation.applied`
记录前后值，并可在同一行撤销。代码、提示词、策略与证据规则不可触及，且不会自行运行。

**依据。** 能自行扩大权限的 Agent 是风险而不是改进回路；权限与完成判定属于 Kernel。摘要
本来就是 Journal 的投影（`loadAudits` / `summarizeAudits`），评审者不需要新数据路径；模型
失败时降级为实测事实（`test/self-review.test.ts`）。

**代价。** 窄接口无法修复代码或提示词缺陷，只能调模型与强度。这是有意的。

**推翻条件。** 若配置接口无法处理某类真实失败，新增动作类型必须单独写取舍并自带校验与
回滚——绝不把这一条扩到代码、提示词、策略或证据规则。

## 2026-11-04 —— 移除哈希 n-gram"语义"召回项

**决定：** 移除。`MdMemoryStore.recall` 保留 bigram 比例、IDF 加权余弦、偏好先验与虚词下限。

**备选：** 保留在 `CLONE_AI_RECALL_SEMANTIC` 开关之后；换成真实 embedding 服务。

**为什么输。** 在 LongMemEval-s（470 道计分题、完整干草堆、maxResults=10）上做消融：

| 指标 | 有语义项 | 无语义项 |
| --- | --- | --- |
| any@1 | 77.9% | 76.6% |
| any@5 | 91.3% | 91.7% |
| any@10 | 95.5% | 94.9% |
| ndcg@10 | 82.0% | 81.5% |
| 上下文命中率 | 92.6% | 92.8% |

差值方向不一致，且在 n=470 时处于噪声范围内。一个无法证明有帮助的排序项，就是每次查询的纯成本
（每个候选多一次 SQL 取数、一张 2048 bucket 的表、约 40 行哈希代码）。

**放弃了什么。** 它本来想覆盖的场景——不共享任何精确词项的改写，例如"周五要交周报了"对
"每周五提交工作汇报"——不再被覆盖。不过在基准上它也从未被证明有效。

**可推翻条件。** 满足任一条：

- 出现真实的 embedding 端点（本地模型或网关能力），并在偏好题切分上胜过词法路径，而偏好题正是
  弱项：any@1 20.0%、any@10 70.0%；
- 出现结构上就不可能有精确词项重叠的产品问题类型（跨语言、大量缩写）；
- 在更大样本（LongMemEval-m）上重跑，差值符号反转。

## 2026-11-04 —— 保留 IDF 加权余弦项

**决定：** 保留在 `recall` 中。

**为什么赢。** 它不会引入任何不共享词项的记忆，最坏情况只是重排已经匹配上的记忆；同一次改动中加入的
虚词下限消除了它真正的失效模式（单个 "the" 就能通过 0.2 比例下限）。

**放弃了什么。** 每次召回、每个候选多一次 SQL 查询。

**可推翻条件。** 值得单独重测；若同样没有收益，按与语义项相同的标准移除。

**状态：** 目前是推测——尚未单独测量。

## 2026-11-04 —— 记忆推入 Main Agent 的 Prompt，而不是只留给拉取

**决定：** 每个回合由 `before_agent_start` 把匹配的记忆重新编译进 System Prompt。

**备选：** 只保留 `recall_memory` 工具路径；改为注入一条 user 角色消息。

**为什么赢。** 只拉不推意味着所有者批准过的记忆仍可能被当作不存在。走 System Prompt 复用了 Worker
已有的 1200 字符 / 6 条边界，且不改动对话历史（注入 user 消息会出现在对话记录与 `readConversation` 中）。

**放弃了什么。** 每回合一次召回（短生命周期 SQLite 句柄）；System Prompt 逐回合变化，削弱 Prompt 缓存。

**可推翻条件。** 若每回合延迟变得明显，或 Prompt 缓存节省的收益压过推送准确度。

## 2026-11-05 —— 一致性被测量，而首次运行四个场景挂了三个

**决定：** `npm run bench:consistency` 用真实的召回 + 上下文 + 注意力路径跑四个一致性场景与两个克制场景。

**首次运行测到了什么。** 一致性 1/4 通过，无关观察变成打扰的比例 100%。三个失败都是真的：

- 改期后的会议与旧时间同时进入上下文；
- 改过的偏好与旧偏好互相竞争；
- 一条明确声明的偏好，面对长问题时根本没被召回。

**据此改了什么。**

- 偏好可以在产品下限之下被召回（0.08 而非 0.2），但只限**有区分度**的命中——该词被库中至多四分之一的记忆共享。
  实测：没有区分度检查时，更低的下限会让闲置记忆显得被用过，从而破坏闲置归档。中文虚词 bigram（必须、应该、时候）
  也加入拉丁停用词表已有的排除范围。
- 使用明确替换动词（改到、改用、不再、"changed to"）的较新记忆，会让同类型、共享实词的较旧记忆**仅在上下文中**退役。
  仅凭相似度做不到："周五下午三点开会"与"周五的会改到周四下午"十几个词里只共享两个，所以信号是动词本身。
- 观察只有在文字要求做决定时（截止、确认、due、invoice……）才挣得一次打扰，其余都是背景。

**放弃了什么。** 不用任何词就完成取代的记忆（"会改期了"）仍会让两条都在上下文里。看起来紧急却不含任何信号词的邮件会被漏掉。
两者都如实记录，没有隐藏。

**可推翻条件。** 三个场景中任何一个回归，就是重新审视对应修法的信号；语义比较器可以让取代规则不再依赖动词。

## 2026-11-05 —— 步内续跑：刻意不做

**决定：** 步骤中途死亡的 Worker 要么整步重跑（有重放安全保证时），要么失败；没有任何 Adapter 会在步内续跑。

**为什么。** 真正可强制的是两个边界——步骤与 Run。在步骤**内部**续跑意味着信任 Worker 对"自己走到哪了"的说法，
黑盒 CLI 无法给出这种说法，原生 Worker 则必须在每个副作用之前写入检查点协议。当前策略（仅在有重放安全保证时
重新入队；外部副作用或验证中途一律失败）是对同样事实的保守解读。

**放弃了什么。** 一个跑到 90% 才死掉的长步骤要重新付一次代价。对原生 Worker 而言，这由时长预算约束，而不是由正确性约束。

**可推翻条件。** 若长步骤变得常见且重跑昂贵，应给 `NativeModelClient` 增加显式检查点——由 Worker 自己写入并能自行校验的
可续跑会话状态——绝不从工作区状态去猜。

## 2026-11-05 —— 日历与邮件以只读 Connector 接入

**决定：** `CalendarConnector` 从文件或 https URL 读取 ICS；`EmailConnector` 读取 IMAP 的 INBOX。
两者都不能写入、不能接受邀请、不能发信。凭据只以变量名出现（`env`），在构建时从进程环境读取；
变量缺失时该 Connector 保持禁用并说明原因。

**为什么用 ICS 与 IMAP 而不是厂商 API。** 一个读取器就能覆盖 Apple、Google、Outlook、Nextcloud 的
导出，无需 OAuth、厂商 SDK，也不存 token 刷新流程。IMAP 是每个邮箱都支持的协议。

**放弃了什么。** 没有推送：两者都在维护扫描中轮询，日历变化要等一个间隔，而非即时。邮件只取摘要而非
完整正文，也没有附件。邮件只读，所以"替我回复"仍是一个需要所有者批准的独立工作单——这是刻意的，
但也意味着分身还不能端到端地回复一封邮件。

**可推翻条件。** 若回复成为产品需求，应新增带 Receipt 的动作 Connector，而不是给这个观察 Connector
加写入方法。

## 2026-11-05 —— 记忆上下文预算按类别分配

**决定：** 偏好可占剩余额度的 50%，任务结果 25%，项目事实 20%，Agent 结果 5%，按此顺序填充，用不完的额度向后顺延。

**为什么。** 统一的 1200 字符上限让一周已完成任务的日志挤掉了那条本会改变回答的偏好；在 LongMemEval 上偏好题正是最差的一档，
上下文命中率 56.7%，其他类型 92–99%。

**放弃了什么。** 排序不再纯按相关度：一条高分的任务记忆可能被一条低分的偏好挤掉。这是有意的取舍，但也意味着针对近期任务的
调试问题，看到的相关任务上下文会比以前少。

**可推翻条件。** 若上下文边界基准在任务类问题上出现回归，就提高任务结果的份额，或让权重取决于意图。

## 2026-11-05 —— 冲突检测就是词重叠，并如实说明

**决定：** `findConflicts` 在同类型的活跃记忆之间比较词重叠（重叠系数）；≥0.55 为近似重复，≥0.35 为值得复核的同一主题。
匹配上的复述会在构建上下文前从召回集中丢弃。

**实测局限。** 改写句 0.57–0.93；无关句 0.0–0.4。中文里的**取值改变**（"蓝色" -> "绿色"）只有 0.29，因此**无法可靠捕获**——
不同的取值在两端各替换了一个 bigram。测试只断言能工作的情形，并在注释中说明；不去断言不工作的情形。

**放弃了什么。** 措辞不同的矛盾仍无法检出，可能同时被召回。缓解：一旦检出就只保留一条；且冲突以复核建议呈现，而不是自动删除。

**可推翻条件。** 一个基于 embedding 的比较，在同一批配对上能捕获上述取值改变的情形。

## 2026-11-05 —— 取代上一条：对话提炼默认走廉价本地过滤

**决定：** `CLONE_AI_MEMORY_MINING` 现在是三档开关。未设置 = `filtered`：回合里含"持久陈述信号"时
才提炼（`src/memory/mining-policy.ts`）；`off` 同时关闭对话与任务提炼；`all` 每轮都提炼。任务提炼
除非处于 `all`，仍使用确定性 Worker。

**为什么改变上一条。** "显式开启"意味着个人 Agent 最需要的能力——无需被要求也能学习——开箱即关闭。
过滤器在本地运行、不产生模型调用，且宁可多提炼：漏掉一条陈述就是一条永远学不到的记忆，多一次调用只是几分钱。

**放弃了什么。** 没有信号的回合永不被提炼，因此一条陈述得很直白却不含任何匹配模式的记忆可能被漏掉。
`all` 是逃生门。

**可推翻条件。** 若实践中发现过滤器的漏检明显，就扩充信号列表，或把 `all` 设为默认。

## 2026-11-04 —— 对话提炼默认关闭（`CLONE_AI_MEMORY_MINING=1`）

**决定：** 与任务提炼一致，默认关闭。

**为什么赢。** 每个所有者回合一次模型调用。默认开启会把预算花在没产生值得记住内容的对话上。

**放弃了什么。** 开箱即用时，分身不会从对话中学习——这是与陪伴类产品最大的功能差距。

**可推翻条件。** 一旦有廉价或启发式的前置过滤能排除明显不含持久陈述的回合，提炼器即可默认开启。

## 2026-11-04 —— 失败聚类的教训通过 author 写入，而非提炼候选

**决定：** 同一失败签名出现 3 个以上 Run 时，经所有者批准通过 `MemoryGovernance.author()` 写入一条
`procedure` 记忆，而不是作为提炼候选。

**为什么赢。** 提炼候选只能引用自己 Run 的证据；聚类横跨多个 Run，没有单个 Run 能为其作证。所有者的批准
就是证据。

**放弃了什么。** 教训文本是模板拼出来的（类别、次数、签名、目录建议），而不是模型撰写。

**可推翻条件。** 若教训质量比引用纯度更重要，可允许带显式证据集的跨 Run 候选。

## 2026-11-04 —— 原生 Worker 靠环境变量开启，而非默认

**决定：** `CLONE_AI_NATIVE_MODEL` + `CLONE_AI_NATIVE_BASE_URL` 显式开启；否则 Registry 继续使用
沙箱化的 CLI Worker。

**备选：** 作为默认；总是注册但在派发时失败。

**为什么赢。** CLI Worker 有 OS 强制边界；原生 Worker 的边界由我们自己的代码保证。在它积累生产里程之前，
更安全的默认应当是有沙箱的那一个。

**放弃了什么。** 需要理解两种 Worker；原生路径尚未在大规模下验证。

**可推翻条件。** 原生 Worker 跑过真实所有者任务且没有边界回归后，可成为非编码任务的默认。

## 2026-11-04 —— 归档而不是删除

**决定：** 过期、闲置、淘汰都只归档，不销毁。

**为什么赢。** `memory.restored` 使每个决定都可回滚，Journal 也因此诚实地记录了分身曾知道什么。

**放弃了什么。** 原则上磁盘占用无上限。

**可推翻条件。** 增加"归档超过 N 年的记忆清理"，需所有者明确同意并记录原因。

## 2026-11-04 —— 90 天寿命与 90 天闲置

**决定：** 提升的记忆默认 90 天过期；任何活跃记忆 90 天未被使用即归档。

**为什么赢。** 90 天对应一个项目、一个工作周期或一个学期——所有者本人的说法。

**放弃了什么。** 一条仍然为真、只是 90 天内没被召回的事实会从召回中消失。可恢复，但需要所有者注意到。

**可推翻条件。** 若改进环路的使用数据显示被恢复的记忆其实仍有用，就延长窗口或豁免手写记忆。

**状态：** 90 天这个数字来自所有者的描述，是推测值，未测量。

## 2026-11-04 —— 所有者标签高于系统验证

**决定：** 结局归因中以 `audit.labeled` 判定好坏，系统验证作为兜底。

**为什么赢。** 标签是评估用来对照系统的真值。两者不一致时，按定义系统是错的。

**放弃了什么。** 一次草率的标签会污染该 Run 暴露过的每条记忆的归因。

**可推翻条件。** 若标签被证明噪声大，对已完成 Run 的 `fail` 标签要求附注或二次确认。

## 2026-11-04 —— 改进建议是确定性的，且待决上限 10 条

**决定：** 建议 id 由依据推导（`retire:<id>@<bucket>`），同时最多 10 条待决。

**为什么赢。** 每次扫描重算不能产生重复；建议泛滥会训练所有者盲目通过，等于废掉门禁。

**放弃了什么。** 一条真正新的建议可能被推迟到旧建议被决定之后。

**状态：** bucket 大小与上限 10 都是推测值，尚未调参。

## 2026-11-05 — 按 runId 和文件指纹消费已修复轨迹

**决定。** 为每个 runId 保存最近一次成功批次的结果和原始输入文件 SHA-256；只有
两者都匹配时才跳过。仅 `fixed`、`pr-created`、`patch-only` 会消费，错误仍可重试。
使用同目录重命名持久化；文件不可读或格式错误时按空状态处理。

**依据与备选。** 当前 `loadTraces` 没有先前结果记录，会再次送修未变化的轨迹；
这是代码观察，不是生产事故测量。一直重试浪费修复工作，只记 runId 则会漏掉新内容。
完整的模型依赖流程超出本次离线任务，效果仍属**假设**。状态丢失或损坏可能导致重复工作；
成功结果之后的其他步骤失败不会撤销成功记录。

**推翻条件。** 如果需要跨机器共享的持久账本，或轨迹导出经常改变字节但有效证据不变、
因而反复触发修复，就替换这一文件方案。

## 2026-11-06 —— 修复通道是 Clone AI 自己的 Run，而不是脚本驱动另一个 CLI

**决定。** `clone-ai repair` 把修复做成 Kernel 内的真实 Run：接受 Trigger、挂上两阶段计划，
用所有者实际配置的 Worker（黑盒 CLI Worker，或其他已注册 Adapter）执行。通道保留
`scripts/nightly-rsi.mjs` 已有的闸门（回归测试先验证为红、测试文件哈希、暂存差异不得触碰保护
路径），做法是导入 `scripts/nightly-rsi-policy.mjs` 与 `scripts/nightly-rsi-state.mjs` 而不是
另抄一份；worktree 隔离、红色验证与哈希由应用在 Run 周围及之后作为确定性闸门执行。

**被否决的备选。**（a）继续用 `claude -p` 当执行者——那么 AGENTS.md 第 4 条描述的是系统无法满足的
规则，且修复并非由 clone-ai 完成。（b）强制使用进程内原生 Worker（OpenAI 兼容）——它便于测试，
但会把修复回路绑到单一 Provider，以及多数机器上并不存在的 `CLONE_AI_NATIVE_*` 配置；它仍可作为
已配置 Worker 使用。（c）为通道另建一套策略模块——第二份保护路径清单会与夜间脚本执行的那份漂移。

**依据。** 代码观察：`scripts/nightly-rsi.mjs` 自行拼 Prompt 并 spawn 二进制，Kernel 的审批、
验证与 Journal 都不参与修复。这里原样导入其安全闸门，由既有 `test/nightly-rsi.test.ts` 断言覆盖。
确定性测试用假 Adapter 证明每条通道闸门（`test/repair.test.ts`）。真实两阶段修复需要已配置 Worker
与一条已授权的失败轨迹；已配置模型能否产出可接受的补丁仍是**假设**，本次未测量。

**放弃了什么。** 通道现在继承 Kernel 的 Worker 配置与 Adapter 契约，因此没装任何 Worker CLI 的机器
无法修复，而旧脚本只需 PATH 上有 `claude`。黑盒 Worker 从不报告 `test` 证据，所以"验证测试为红"
这类检查必须由应用在 Run 周围完成，而不是交给 Verifier——Run 自身的步骤只负责写文件。

**推翻条件。** 如果 Kernel 路径无法表达一次修复（步骤数远超计划能容纳的规模，或 Adapter 契约
承载不了哈希），就把两个阶段退回脚本，但保留共享的轨迹导出与策略模块。如果测量显示已配置 Worker
修复真实轨迹的通过率不可接受，而直连原生客户端可以，就把原生 Adapter 设为默认执行者而不是回退项。

## 2026-11-06 —— MCP 工具按服务器显式开启，并与内建工具过同一道闸门

**决定。** 增加一个小型 MCP 客户端（stdio，另支持 streamable HTTP），读取
`<clone home>/mcp.json`。除非所有者为某个服务器写 `"enabled": true`，否则一律关闭。MCP 工具被转换成
带显式风险的 `NativeToolSpec`（`read`、`write`、`network`、`external`），只有 `decideTool` 核对
步骤授权后同意该风险，才会提供给 Worker；点名路径的调用与 `read_file` 一样逐次核对。MCP 输出走
观察边界（`sanitizeObserved`，即 `renderObservationsAsFacts` 用的同一个清洗函数），以引用数据的形式
到达模型。无法接受 `--mcp-config` 的 Provider（进程内原生 Worker、codex、pi）只会拿到内建工具。

**被否决的备选。**（a）引入 SDK 依赖（`@modelcontextprotocol/sdk`）——我们需要的协议只是每个工具一次
JSON-RPC 请求（`initialize`、`tools/list`、`tools/call`），走 stdio 或 HTTP；只有当 resources、prompts、
sampling 或 OAuth 进入范围时，依赖才值得。（b）默认开启所有已配置服务器——MCP 服务器是所有者并未
编写的工具面，默认开启等于悄悄扩大模型能做的事。（c）因为传输层是网络就默认给 MCP 工具网络权限——
风险属于工具声明的行为，由所有者在配置里逐个写明。

**依据。** 代码观察：今天的工具表只来自 `src/main-agent/tools/kernel-tools.ts` 与
`src/workers/native-worker-factory.ts`，且原生 Worker 已会拒绝未授权的风险（`decideTool`）。测试覆盖
默认关闭、授权不足时拒绝、授权存在时提供、以及输出包裹（`test/mcp.test.ts`）。真实第三方 MCP 服务器的
工具在这些风险下是否好用仍是**假设**。

**放弃了什么。** 服务器必须在 `mcp.json` 里声明每个工具的风险（通道从不猜测：未声明的工具按
`external` 处理并拒绝）。工具结果只有文本——图片与结构化内容会被字符串化。服务器崩溃以工具错误
上报，不重试。

**推翻条件。** 若真实 MCP 服务器需要 resources 或 prompts（改用维护中的 SDK，而不是扩展本客户端），
或所有者普遍把每个工具都标成 `read` 来省掉风险配置——那时风险必须来自签名的服务器清单，而不是所有者
配置。
