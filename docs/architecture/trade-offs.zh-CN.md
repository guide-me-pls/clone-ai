# 架构取舍

[English](trade-offs.md) · **简体中文**

只有把理由写下来，一个决定才算真正稳定。每条记录都说明决定了什么、依据是什么，以及在
什么条件下后来者应当推翻它。

## 2026-11-09 — 模型可以派发任务，但只有 Kernel 规划与判定完成

**决定。** 增加一个模型可调用的 `dispatch_task` 工具，把目标与验收标准转成与 companion
相同的 `runQuery` 路径。它不是第二个执行面：规划、权威、预算、证据验证与完成判定仍归
Kernel。对话仍要直接回答；已经知道确切步骤的计划仍走 `propose_work_plan`。

**依据。** 审计发现 Main Agent 能提案计划，却不能自己开始工作
（`docs/study/claude-code-parity.md`，缺口 #6）。`runQuery` 已经拥有触发 → 召回 → 规划 →
执行 → 验证，复用它保持只有一条完成路径。备选方案——让 Main Agent 直接启动 Worker——
会造出第二个权威与第二个可以宣布任务完成的地方。

**代价。** 从模型视角看第一次派发是同步的，长任务会占住回合；后台派发与完成通知是下一步，
不在本次范围内。工具也只接受目标与标准，模型无法表达逐步骤 scope；需要那种精度时必须用
`propose_work_plan`。

**推翻条件。** 如果真实任务经常需要逐步骤授权或后台完成，就给 `dispatch_task` 增加后台
选项并立刻返回 run id；如果同步调用被证明是超时来源，就把后台作为默认。

## 2026-11-09 —— 回归用例进入默认测试集

**决定：** `npm test` 现在同时运行 `test/*.test.ts` 与 `test/regression/*.test.ts`。

**依据：** 2026-11-06 合并的两个桌面修复带了用例，但 `npm test`、`npm run gate` 与 CI 此后都不会再跑它们：
glob 是 `test/*.test.ts`，不匹配子目录。未来的改动可以重新引入这两个缺陷，而所有自动检查仍是绿的。

**放弃了什么。** `npm test` 稍慢（多两个文件），且一个故意为红的回归用例无法在不使默认套件失败的情况下合并。
这正是目的。

**可推翻条件。** 若回归目录大到拖慢默认循环，把它移到第二个脚本，由 CI 与 `npm test` 并列运行，绝不能移出 CI。

## 2026-11-09 —— 后台重绘让位于正在输入的编辑器

**决定：** 记忆面板的 `render()` 接受 `{ background: true }`，仅轮询包装使用；当焦点位于 `#memory-root` 内的
`INPUT` 或 `TEXTAREA` 时，后台重绘被跳过。

**依据：** 2026-11-06 的修复比较整段标记，只在“什么都没变”时跳过。用同一沙箱做的探针显示：任何真实变化
（另一条记忆的 `updatedAt`，或被召回增加的 `accessCount`）都会重建 DOM 并摘下未保存的编辑器。由于每次召回都会
改变计数，原缺陷在正常使用中仍会触发，只是频率更低。

**放弃了什么。** 所有者输入期间，面板自身内容不更新（加载完成的详情要等焦点离开后才出现）。这与 `app.js` 中
`renderLibrary` 的守卫一致，且优于丢失编辑。

**可推翻条件。** 若“输入时内容 stale”成为抱怨，正确的修法是在重绘时保留焦点节点（原地更新），而不是移除守卫。

## 2026-11-09 —— write_file 的覆盖模式按 Worker 区分，只有修复通道拒绝

**决定：** `fileTools({ writeFileMode })` 默认 `overwrite`；`createConfiguredNativeWorker` 读取
`CLONE_AI_NATIVE_WRITE_FILE`，修复通道为自己的进程设为 `refuse-existing`。

**依据：** 2026-11-06 的改动让 `fileTools()` 无条件拒绝已有路径。这保护了只需要片段编辑的修复通道，但也让每个
普通任务失去了重新生成已有文件的能力——且没有删除工具，任务无从恢复。

**放弃了什么。** 需要理解两种模式，以及修复进程中的一个环境变量。修复不再能合法地整文件替换；这是有意的限制。

**可推翻条件。** 若修复经常需要整文件替换，新增一个仅对修复通道开放、自带大小校验的 `replace_file` 工具，
而不是对所有 Worker 放宽 `write_file`。

## 2026-11-06 — 采纳 Claude Code 的 harness 机制，不采纳其源码与 Prompt

**决定。** 把逆向得到的 Claude Code 2.1.317 机制当作 clone-ai 自己的 Agent 循环的参考规格：
带类型的终止原因、流式工具调度与逐工具并发标记、逐次权限管线、token 感知压缩、hook、MCP、
Skills。不把源码、Prompt 原文或 Anthropic 内部配置复制进本仓库。

**依据。** 提取出的 Bun 模块图有 2,942 个模块，并带有版权声明（`cli`：
“(c) Anthropic PBC. All rights reserved.”）。机制以字符串常量与控制流可见
（`BUILTIN_TOOL_NAMES`、六模式权限枚举、33 个 hook 事件名、`effectiveWindow - 13000`
压缩数学）。clone-ai 的 README 声明它不嵌入其他 runtime，Claude Code 是黑盒 Worker。
复制 Prompt 还会把个人分身的 charter 换成编码 CLI 的身份。

**代价。** 重写比嵌入 `@anthropic-ai/claude-agent-sdk` 慢；对齐必须由 clone-ai 自己的 eval
证明，不能从 Anthropic 继承。

**推翻条件。** 如果所有者明确选择“先要速度、后要独立”，并接受仅 Anthropic 的凭据与
Provider 路径，可以把 Agent SDK 作为临时参照/基准路径，而不是产品架构。

## 2026-11-06 — 执行 Worker 是通用的，编码只是其中一种工具配置

**决定。** 保留 Main Agent 的提案/权威边界，增加模型可调用的 `Task`/子 Agent 路径与只读
检查工具。把 Worker 当作通用执行面：工具集由角色与能力配置决定，不硬编码成编码。编码配置
（Read、Write、Edit、Glob、Grep、Bash）只是其中一种；research、review、draft 与外部连接器
各有自己的配置。不直接给 Main Agent Bash/Edit/Write。

**依据。** `src/workers/native-agent-worker.ts` 已经接受任意 `NativeToolSpec[]` 与
`workCapabilities` 列表；`fileTools()` 只是当前默认配置，不是类型层约束。`decideTool` 按
风险、路径与网络 scope 逐次放行，因此更大或不同的配置不会扩大权威。README 的不变量是
“Main Agent 是大脑，永远不是权威”。Claude Code 自己的 coordinator prompt 也把 coordinator
与 worker 分开（`chunk-mas5an83.js`），与 clone-ai 的现有拆分一致。

**代价。** 配置需要所有权、版本与测试；角色拿错配置会过强或过弱。Main Agent 不能自己检查
文件，除非新增只读工具。

**推翻条件。** 如果同模型基准显示 orchestrator 往返让任务成功率下降超过 20%，或让中位
延迟翻倍，就在同一逐次闸门下允许 Main Agent 直接执行只读工具。

## 2026-11-06 — Main Agent 与原生 Worker 共享一个 Agent 循环内核

**决定。** 抽出 `src/agent/loop.ts` 状态机，带类型终止原因、工具调度、预算检查、abort 传播、
重试策略与压缩钩子。`runNativeMainAgentTurn` 与 `OpenAiCompatibleClient` 变成它的适配器。

**依据。** 现有两个循环重复了 SSE/非流式请求处理、用量统计与 8,000 字符工具结果截断
（`native-runtime.ts:270-315`、`openai-compatible-client.ts:74-96`）；两者都缺同样的能力。
`native-runtime.ts` 的头注释说“no compaction”，文件却在 `:515-558` 压缩——这正是重复会
产生的漂移。Claude Code 的终端、SDK 与桌面共用一个查询循环（`chunk-8ntpzya9.js`）。

**代价。** 重构两条热路径，期间行为必须由测试钉住；循环不能长出 Provider 专属分支。

**推翻条件。** 如果 Main Agent 与 Worker 在传输或流式要求上分叉（例如某个 Provider 不能
流式返回工具调用），保留不同的模型适配器，但共享调度、预算与工具结果层。

## 2026-11-06 — 每个进程内工具调用都经过逐次决定

**决定。** 所有进程内工具调用都经过 `ToolAuthority`（或后继策略 broker），返回
`{behavior: allow | deny | ask, reason, updatedInput?}`。计划时策略仍是外层闸门；hook 可以
添加上下文或拒绝，但不能静默扩大权限。

**依据。** `src/core/tool-authority.ts` 存在，但只被 `test/tool-authority.test.ts` 引用；
`runNativeMainAgentTurn` 会执行模型点名的任何工具（`native-runtime.ts:292-308`）。
Claude Code 逐次经过规则、模式与 `canUseTool` 决定，被拒绝的调用作为工具结果返回模型，
回合继续（`chunk-q8qwkppc.js`）。审计把它列为缺口 #2。

**代价。** 每次调用有更多事件与延迟；桌面与 CLI 需要 `ask` 路径，每个工具需要风险分类。

**推翻条件。** 如果逐次闸门让只读批次的延迟增加超过 10%，且红队演练没有阻止任何真实事故，
就允许只读批次在一份计划时授权下运行，但写入、shell、网络与外部动作仍保留逐次闸门。

## 2026-11-06 — 压缩按 token 计算并落记录；先确定性摘要

**决定。** 按配置的上下文窗口估算 token，用 Claude Code 推导的阈值压缩
（`effective = window - min(maxOutputTokens, 20000)`，
threshold `min(floor(effective * (1 - 0.2)), effective - 13000)`，
`threshold - 20000` 警告，`effective - 3000` 阻断），写入带保留消息 id 的 `compaction`
记录，默认使用确定性摘要。只有在 eval 证明模型摘要更能保留任务关键事实后，才加入模型摘要。

**依据。** 原生循环按字符压缩历史（`historyChars ?? 12000`，最新 66% 原文），且从不写
`compaction` 记录（`native-runtime.ts:238-241,515-558`）；桌面上下文面板读的是遗留 Pi
JSONL（`conversation-history.ts:241`）。Claude Code 写入带 `preservedMessages.uuids` 的
`compact_boundary`、九段摘要与保留尾部。确定性摘要私密、便宜、可测试；模型摘要增加成本与
非确定性。

**代价。** token 估算近似；确定性摘要可能丢细节；`compaction` 记录增加一种持久事件。

**推翻条件。** 如果长上下文基准显示，在至少 20% 的种子用例中确定性摘要丢掉的事实能被
模型摘要保留，就对超过阈值的会话默认使用模型摘要。

## 2026-11-06 — 先做 MCP 与 Skills；插件、云、VM、computer-use 延后

**决定。** 先实现进程内 MCP host（stdio，然后 HTTP/SSE）与带渐进披露的 `SKILL.md` 加载器
（P1）。把插件市场、云会话、VM 沙箱、Chrome 集成与 computer-use 延后，直到加权 harness
分至少 90 且真实工作流需要它们。

**依据。** clone-ai 没有 MCP 或 Skills 代码（审计：扩展点 10/100）。MCP 与 Skills 是
Claude Code 的扩展入口，第三方集成几乎都从这里进来。插件与云/VM 是有基础设施成本的产品面；
macOS Seatbelt 已经隔离 CLI Worker（`authority/seatbelt.ts`），而 Claude Desktop 的 VM 是
26 MB 镜像加平台相关 hypervisor 代码。延后它们，避免把对齐预算花在不动 harness 分数的
基础设施上。

**代价。** 在这些阶段之前，用户不能安装第三方插件或运行远程/浏览器工具；MCP 增加攻击面，
Skills 可以注入指令。

**推翻条件。** 如果所有者的真实工作流依赖某个插件/市场或远程 MCP，就提前该集成；如果红队
测试绕过 Seatbelt，就提前 VM 沙箱。

## 2026-11-06 — 95% 是加权 harness 对齐分

**决定。** 把对齐定义为 12 维加权分 ≥ 95、每维 ≥ 80，并且同模型实机基准不低于 Claude Code
参照运行。模型质量单独测量、单独报告，绝不混进 harness 分数。

**依据。** clone-ai 支持任意 OpenAI 兼容端点；其模型可能比 Claude Code 默认模型弱或强。
把模型质量与 harness 质量混在一起，分数不可比，还会让弱模型替循环背锅。提取出的 harness
机制才是可控变量。

**代价。** 分数需要维护 eval 套件与实机参照；权重可以被操纵，因此评分细则要求每级有可执行
证据，并设置每维下限。

**推翻条件。** 如果同模型对比显示 clone-ai 任务通过率至少 95%，而清单分低于 85，就按任务
成功率重新加权；那时的清单测的是用户不在乎的东西。

## 2026-11-06 — Worker 并发跟随实测机器容量，硬上限由 Kernel 掌握

**决定。** Kernel 采样 CPU 并行度、负载均值与空闲内存，计算并发 Worker 上限，并通过共享
限流器约束每次 Worker 执行。主 Agent 可以通过只读的 `get_capacity` 工具看到同一份快照，
从而决定计划规模，但不能提高上限。所有者可用 `maxConcurrentWorkers` 固定上限；`0` 或未
设置表示自动。

**为什么。** 所有者要求派发并发跟随内存与 CPU，以充分利用本机。让模型直接决定并发数，
会让并发取决于一次采样出的 token 而不是机器：它可能把笔记本压进 swap，也可能把大工作站
误判成串行。实测容量是确定性的、可测试的，且对每个调用方是同一个答案；模型的角色仍是它
本来该做的——决定提出多少工作。

**依据。** 改动之前，`executeSubagents` 用 `Promise.all` 跑所有就绪工作单，队列每个 tick
启动所有排队 Run，因此并发度只来自计划形状。16 核主机与 2 核主机表现相同。

**代价。** 限流器带来排队：Run 可能等待空位而不是立即开始。同一 Workspace 内的只读子
Agent 仍共享写锁，因此即使还有容量，同 Workspace 的写步骤仍是串行。

**推翻条件。** 若运行期测量在所有者硬件上不准（cgroups、容器限制或噪声邻居），让所有者
固定 `maxConcurrentWorkers`，把自动模式视为建议；或用观测吞吐量的反馈环替代公式。绝不让
模型设置硬上限。

## 2026-11-06 — 只保留自己的 Agent：去掉 Pi SDK 与黑盒 CLI

**决定。** 从代码路径中移除 Pi Agent SDK，以及所有黑盒 CLI Worker（Claude Code、
Codex、Pi CLI、opencode）。主 Agent 只运行进程内的原生循环；每个执行角色只运行原生
Worker。external 角色在有受治理的动作连接器之前没有 Provider，而不是回退到 CLI。

**为什么——所有者的理由。** 藏在 CLI 后面的子 Agent 不可控：它的工具调用对 Kernel
不可见，凭据活在那个进程里，安全规则只是 Prompt 文本而不是闸门。主 Agent 是特殊的：
它只能分发任务、组装上下文，绝不执行，因此它的循环、上下文组装与工具面必须是我们
自己的、可审计的，而不是委托给 SDK。保留 CLI 作为回退，会原样保留这次变更要移除的行为。

**被否决的备选。** （1）保留 Pi 作为回退：只要原生端点不可用，回退就会变成事实路径，
不可控行为随之回来。（2）只为外部动作保留 CLI：外部副作用会在没有 Receipt、没有逐次
闸门的情况下运行，这是风险最高的路径。（3）给 CLI 套一层策略代理：仍然看不到单次工具调用。

**依据。** 原生 Worker 通过完整的 5/5 可靠性套件并给出精确用量；原生主 Agent 在五次
样本中与 Pi 同为 15/15 且 tokens 更少；两条原生路径都有流式、压缩与回合/工具/用量事件。
黑盒路径的审计停在进程边界。

**代价。** 主 Agent 需要 OpenAI 兼容端点（`CLONE_AI_NATIVE_*`）；没有端点时，回合会
清晰失败，而不是退化到 Pi。外部动作在有受治理的连接器之前不可用。CLI 独有的能力
（Coding Agent 自己的工具、网络访问）消失。既有 Pi 会话与 CLI Worker 设置不再可用；
回合台账成为对话记录。

**推翻条件。** 只有当替代 Adapter 提供逐次工具可见性、由 Kernel 放行的执行，以及可信
Receipt 时才允许加回；原始 CLI、或拥有循环的 SDK，都不是有效的推翻。如果原生端点无法
做到可靠，产品应当被阻塞，而不是静默降级。

## 2026-11-06 — 主 Agent 对比每格重复多次并报告中位数

**决定。** `npm run bench:main` 对每个任务/运行时组合跑 N 次（默认 5），报告中位数与
p90 耗时、中位 tokens 与通过率，并把每一次运行和聚合结果都写入结果 JSON。
`--repeat 1` 恢复旧的单次形状。

**依据。** 2026-11-05 的两次单次运行对"谁更快"给出相反结论：原生 plan 一格一次 45.2s、
另一次 11.1s；Pi 的 plan tokens 一次 8,977、另一次 13,174。单样本无法给延迟排序；重复
取中位数是让对比有意义的成本最低的方式，而保留每个样本能暴露离散程度。

**代价。** 模型调用与墙钟时间乘以 N（5 次重复约为单次的 5 倍成本）。若端点处于负载中，
中位数仍可能误导，因此报告同时保留每个样本与 p90。

**推翻条件。** 若录制的 cassette 能确定性重放同一组 Prompt，就用它测延迟，本脚本只保留
为真实端点的健全性检查。

## 2026-11-06 — 修复计划告诉 Worker 它的步骤如何被判定

**决定。** 第一阶段的指令现在明确：先写复现文件，再做广泛探索；只读复现用例需要的文件；
`test/regression/` 下留下的每个文件都必须是失败的复现，诊断或探针文件不被接受。验收标准写明
同一条规则，使一个通过的探针无法满足验收。第二阶段同样被告知：只读失败用例与它覆盖的生产文件、
不留下临时文件、不探索 README 或仓库目录、不写取舍条目（工作的 Agent 已在运行前写好）。两个
阶段都被告知没有 shell 工具，因为让 Worker 去"运行 npm test"而它其实做不到，只会诱发探索而不是
编辑。原生 Worker 的 System Prompt 现在声明：需要写文件的步骤在写工具成功之前不算完成，声称做了
但从未落盘的工作属于失败；第一阶段必须在三次工具调用内发出第一次 write。

**被否决的备选。**（a）继续提高轮次预算——24 轮的运行显示模型把多出来的轮次用于读更多文件，
而不是写补丁；再加预算只会买到更多探索。（b）只写验收标准——实践中模型读的是指令，不是验收
列表。（c）事后由通道剔除探针文件——通道不运行就无法区分探针与劣质复现，而且模型仍可能在通道
看到任何东西之前耗尽预算。

**证据。** 同一轨迹用 Magpie `360/deepseek/deepseek-v4.1-flash` 的两次运行：
`1dddd6b4` 用 12 轮只读不写；`426f3d3a` 用满 24 轮阅读（423,163 输入 token），随后写出
`probe-tmp.test.ts`——一个打印 `memory.js` 末尾内容、且会通过的文件。两次都停在闸门
（`regression-missing`、`not-red`）。第三次运行（`f7e07553`）读了 20 个文件、用了 28 轮与
74,641 输出 token，以 `completed` 结束却没有任何 artifact，因此 System Prompt 现在拒绝"声称做了
但从未落盘"的总结。eval 是下一次通道运行：同一轨迹应产出失败的复现。措辞是否足够由那次运行实测，
而不是假设。

**成本与推翻条件。** 无运行时成本；指令只多两行。若 Worker 开始写浅层、能通过的测试，且
"尽早写"的压力被确认为原因，应推翻本条——那种情况下恢复探索指引，并把验收检查做得更强。

## 2026-11-06 — 原生 Worker 接受显式的轮次预算

**决定。** `CLONE_AI_NATIVE_MAX_ROUNDS` 设定一个原生步骤可花费的模型往返次数；未设置或值非法
时保留内置默认 12。`CLONE_AI_NATIVE_MAX_TOKENS` 对单次补全的 token 数做同样的事。修复通道
通过 Worker 环境把轮次预算设为 32，使一次修复能读完失败代码后仍能写下回归用例与补丁。在一次
观察到的调用让步骤停顿超过十分钟之后，token 上限先被设为 16,000；但这对原生 Worker 的整文件
`write_file` 太低——`audit.js`（44 KB）与 `app.js`（118 KB）无法在该上限内重写，因此通道现在
使用 50,000。

**被否决的备选。**（a）把内置默认值对所有原生调用提高到 24——普通对话回合也会获得双倍工具调用，
在没有任何实测收益的情况下扩大循环模型的影响范围。（b）轮次用尽后让通道重试该步骤——Kernel 已
在预算处结束步骤，重试只会加倍模型开销，且不会让 Worker 学到任何东西。（c）在计划里写"请简短"
——当模型确实需要读五个文件时，一句指令无法让 12 轮预算变得够用。

**证据。** 修复运行 `1dddd6b4-a6dd-42b4-bc18-65b795b62148`（2026-11-06）：第一阶段把全部
12 轮用于 `list_directory`/`read_file`（89,845 输入 / 2,366 输出 token，33 秒），没有写出任何
文件，通道停在 `regression-missing`。之后同一轨迹的一次运行让单个 Provider 调用保持打开超过
十分钟，而对同一网关的 2-token 请求 1.9 秒即返回——因此单次补全现在也有上限。eval 为
`test/native-client.test.ts`（客户端在配置的轮次处停止；配置的 token 上限进入请求体；非法值
被忽略）以及每次条目之后的通道运行。

**成本与推翻条件。** 每一轮都是一次 Provider 调用；预算按步骤而非按运行计算，因此一次修复的
最坏情况翻倍。若原生步骤普遍能在 12 轮内完成（此时该开关掩盖的是提示词问题），或观察到 24 轮
步骤在没有产出文件的情况下空转，应推翻本条——那种情况下该修的是计划，不是预算。

## 2026-11-05 — 原生主 Agent 流式输出并做确定性压缩

**决定。** 原生主 Agent 使用 SSE 流式请求并设置 `stream_options.include_usage`，把内容
增量转发给 `onDelta`，按 index 组装工具调用增量，并解析最后的 usage 块。当对话记录超过

原文。全文仍留在回合台账中，可通过 `search_history` 检索。

**依据。** 开关后的原生循环是非流式的，界面在一整轮结束前看起来是冻结的；它也只保留最近
12 轮且不做压缩。Magpie 会返回 OpenAI 风格的 SSE 块，并在设置 `include_usage` 时返回最后

**代价。** 摘要是抽取式并截断的，不是模型撰写，因此对主题与决定的保真度不如 Pi 的生成式
摘要。流式工具调用增量增加了解析复杂度；格式错误的流会让回合以清晰错误失败，而不是猜测。

**推翻条件。** 若长对话质量受损，把确定性摘要替换为一次模型撰写的压缩调用，并保留确定性
版本作为该调用失败时的兜底。

工具调用（参数为脱敏摘要）与终态。既有的 `main-agent-turns.jsonl` 台账由同一个模块写入，
因此界面与 Journal 不会互相矛盾。

**依据。** 改动之前，CLI 与 `npm run main` 只写提示词快照；companion 写的是审计从不读取
的旁路 JSONL；Pi 的 `tool_execution_*` 事件从未被订阅；`usage.recorded` 没有回合 id。于是
其他 Agent 通过 `clone-ai "..."` 做的事，可能完全没有可审计的输入、回复、工具调用或模型
用量。Journal 是 append-only 的真相，回合数据应当放在这里，而不是第二份日志。

**代价。** 输入与回复文本会增加 Journal 体积。它们会被脱敏与截断；完整对话仍保留在事件
所指的 Pi 会话文件中。工具参数只存脱敏摘要，不存原文。

**推翻条件。** 若 Journal 体积成为实际问题，把文本移到内容寻址的回合文件（与提示词快照
同一模式），事件里只保留哈希与定位符。若脱敏对工具参数不够，只保留工具名与哈希。

## 2026-11-05 — 规划孤儿只在保守宽限期后恢复

**决定。** 仅当规划中的 Run 没有计划、没有存活领取，且最后更新已超过 15 分钟时，
才将其标记为失败。先获取恢复领取，再以原子条件写入：如果刷新投影后 Run 发生变化，
拒绝写入。无法提供这种带条件的围栏写入的存储保持不变；执行与验证阶段的恢复不变。

**依据。** 现有恢复只扫描 `running` 和 `verifying`；规划者在生成计划前退出可能使 Run
永久停留在 `planning`。假设普通的无领取规划在 15 分钟内完成属于保守但未经测量的假设；
没有租约的活跃规划仍可能超过这个时间。立即失败或仅凭时间判定会危及新建或已领取的工作。
仅在内存中复查，则可能在写入失败前覆盖并发生成的计划或取消操作。

**推翻条件。** 如果观测到正常的无领取规划超过 15 分钟，应先改用可靠的规划者租约，
或根据实测时长调整阈值，再启用此恢复逻辑。

## 2026-11-05 — 提示词溯源 = 内容寻址文件 + 一条 Journal 事件

**决定。** 每个主 Agent 回合记录 charter 版本、编译后的情境简报、实际注册的工具表、
模型 id 与推理强度。完整材料写入 `<clone home>/prompt-snapshots/<materialHash>.json`；
Journal 追加一条 `main_agent.prompt_snapshot` 事件，携带各项哈希、定位符，以及桌面回合
的 turn id。

**依据。** 改动之前，Journal 能说明 Agent 做了什么、召回什么，却说不清它被告知了什么：
`MAIN_AGENT_CHARTER` 是常量，情境简报只存在于单个会话的内存里，工具表只存在于 Pi 会话
内部。因此失败的一轮无法归因到某一版提示词，两次"改进"也无法与基线比较。Journal 本来
就是 append-only 的真相（[`state-projector.ts`](../../src/state/state-projector.ts) 从
它重建状态），所以溯源应当放在这里，而不是另开一份日志。

**推翻条件。** 如果 Journal 不再是回合级遥测的合适归宿（例如保留策略要求 Run 与回合按
不同周期过期），就把事件迁移到以同一个 `materialHash` 为键的专用存储；哈希方案与文件
布局不依赖 Journal。

## 2026-11-05 — 工具溯源在注册时捕获，而不是维护一份清单

**决定。** `createKernelToolsExtension` 在注册每个工具的同一时刻通过 `onRegister` 回调
上报它。哈希覆盖模型真正收到的名称、描述与参数结构。

**依据。** 手工维护的工具名清单是第二个真相来源，第一次重命名或新增工具时就会悄悄漂移
——而这正是溯源要暴露的不可见变更。回调看到的是被注册的对象本身，因此不可能与会话不一致。

**推翻条件。** 如果工具可以在 `createKernelToolsExtension` 之外注册（第二个扩展工厂，
或 MCP 托管的工具），注册入口就不再覆盖完整工具表；届时快照必须从会话读取工具列表，
而不是依赖回调。

## 2026-11-05 — 回归门禁离线、逐用例、只衡量行为

**决定。** `npm run gate` 对 held-out 夹具重新运行证据验证与权限策略，用所有者标注
校准审计记录，并把每个用例与记录的基线比较。它不调用模型，是 CI 的必需步骤。

**依据。** 本仓库的保证位于模型周围的规则：完成来自证据，权限来自 Scope，所有者判定
来自 `audit.labeled`。这些层是确定性的，因此零成本门禁可以在每次提交时覆盖它们。
依赖 Provider 的评估，恰恰会在 CI 承压时被跳过。

**推翻条件。** 如果录制的轨迹 cassette 能在无网络环境下回放，就在确定性套件旁边增加
轨迹套件。逐用例基线对判断层始终有效。

## 2026-11-05 — 判定变化即使是改进也会让门禁失败

**决定。** `baseline.json` 记录每个用例当前的结果；任何差异——通过变失败或失败变通过
——都会失败，直到在同一次变更中运行 `--write-baseline`。

**依据。** 未经 diff 审查就到达的改进，与一个恰好在夹具集上看起来更好的回退无法区分。
强制更新基线，使审查者必须看到行为差异及其理由。

**推翻条件。** 如果基线变动开始主导审查成本，就按套件拆分，或为每个用例增加明确的
意图说明；不要改成静默自动更新。

## 2026-11-05 — Worker 只继承模型凭据，不继承工具凭据

**决定。** Provider 声明可以点名模型客户端需要的凭据；任何工具凭据（`GITHUB_TOKEN`、
`AWS_*`、`GOOGLE_APPLICATION_CREDENTIALS`、`*_SECRET` 等）在启动前被拒绝，错误信息指向
凭据代管。

**依据。** 带 shell 和 token 的黑盒 Worker 能做该 token 允许的一切；模型需要 API Key 才能
回答，但不需要所有者的代码托管或云凭据。检查发生在构建期、进程存在之前，因此错误声明无法
泄漏进运行中的 Worker（`test/worker-env.test.ts`）。

**代价。** 确实需要工具凭据的 Worker 不能靠继承配置，必须走代管。

**推翻条件。** 若某个可信、范围极窄的操作需要工具凭据，增加经 Kernel 授权后的按次代管注入；
不要重新开启继承。

## 2026-11-05 —— 一致性被测量，而首次运行四个场景挂了三个

**决定：** `npm run bench:consistency` 用真实的召回 + 上下文 + 注意力路径跑四个一致性场景与两个克制场景。

**首次运行测到了什么。** 一致性 1/4 通过，无关观察变成打扰的比例 100%。三个失败都是真的：

- 改期后的会议与旧时间同时进入上下文；
- 改过的偏好与旧偏好互相竞争；
- 一条明确声明的偏好，面对长问题时根本没被召回。

**据此改了什么。**

- 偏好可以在产品下限之下被召回（0.08 而非 0.2），但只限**有区分度**的命中——该词被库中至多四分之一的记忆共享。
  实测：没有区分度检查时，更低的下限会让闲置记忆显得被用过，从而破坏闲置归档。中文虚词 bigram（必须、应该、时候）
  也加入拉丁停用词表已有的排除范围。
- 使用明确替换动词（改到、改用、不再、"changed to"）的较新记忆，会让同类型、共享实词的较旧记忆**仅在上下文中**退役。
  仅凭相似度做不到："周五下午三点开会"与"周五的会改到周四下午"十几个词里只共享两个，所以信号是动词本身。
- 观察只有在文字要求做决定时（截止、确认、due、invoice……）才挣得一次打扰，其余都是背景。

**放弃了什么。** 不用任何词就完成取代的记忆（"会改期了"）仍会让两条都在上下文里。看起来紧急却不含任何信号词的邮件会被漏掉。
两者都如实记录，没有隐藏。

**可推翻条件。** 三个场景中任何一个回归，就是重新审视对应修法的信号；语义比较器可以让取代规则不再依赖动词。

## 2026-11-05 —— 步内续跑：刻意不做

**决定：** 步骤中途死亡的 Worker 要么整步重跑（有重放安全保证时），要么失败；没有任何 Adapter 会在步内续跑。

**为什么。** 真正可强制的是两个边界——步骤与 Run。在步骤**内部**续跑意味着信任 Worker 对"自己走到哪了"的说法，
黑盒 CLI 无法给出这种说法，原生 Worker 则必须在每个副作用之前写入检查点协议。当前策略（仅在有重放安全保证时
重新入队；外部副作用或验证中途一律失败）是对同样事实的保守解读。

**放弃了什么。** 一个跑到 90% 才死掉的长步骤要重新付一次代价。对原生 Worker 而言，这由时长预算约束，而不是由正确性约束。

**可推翻条件。** 若长步骤变得常见且重跑昂贵，应给 `NativeModelClient` 增加显式检查点——由 Worker 自己写入并能自行校验的
可续跑会话状态——绝不从工作区状态去猜。

## 2026-11-05 —— 日历与邮件以只读 Connector 接入

**决定：** `CalendarConnector` 从文件或 https URL 读取 ICS；`EmailConnector` 读取 IMAP 的 INBOX。
两者都不能写入、不能接受邀请、不能发信。凭据只以变量名出现（`env`），在构建时从进程环境读取；
变量缺失时该 Connector 保持禁用并说明原因。

**为什么用 ICS 与 IMAP 而不是厂商 API。** 一个读取器就能覆盖 Apple、Google、Outlook、Nextcloud 的
导出，无需 OAuth、厂商 SDK，也不存 token 刷新流程。IMAP 是每个邮箱都支持的协议。

**放弃了什么。** 没有推送：两者都在维护扫描中轮询，日历变化要等一个间隔，而非即时。邮件只取摘要而非
完整正文，也没有附件。邮件只读，所以"替我回复"仍是一个需要所有者批准的独立工作单——这是刻意的，
但也意味着分身还不能端到端地回复一封邮件。

**可推翻条件。** 若回复成为产品需求，应新增带 Receipt 的动作 Connector，而不是给这个观察 Connector
加写入方法。

## 2026-11-05 —— 记忆上下文预算按类别分配

**决定：** 偏好可占剩余额度的 50%，任务结果 25%，项目事实 20%，Agent 结果 5%，按此顺序填充，用不完的额度向后顺延。

**为什么。** 统一的 1200 字符上限让一周已完成任务的日志挤掉了那条本会改变回答的偏好；在 LongMemEval 上偏好题正是最差的一档，
上下文命中率 56.7%，其他类型 92–99%。

**放弃了什么。** 排序不再纯按相关度：一条高分的任务记忆可能被一条低分的偏好挤掉。这是有意的取舍，但也意味着针对近期任务的
调试问题，看到的相关任务上下文会比以前少。

**可推翻条件。** 若上下文边界基准在任务类问题上出现回归，就提高任务结果的份额，或让权重取决于意图。

## 2026-11-05 —— 冲突检测就是词重叠，并如实说明

**决定：** `findConflicts` 在同类型的活跃记忆之间比较词重叠（重叠系数）；≥0.55 为近似重复，≥0.35 为值得复核的同一主题。
匹配上的复述会在构建上下文前从召回集中丢弃。

**实测局限。** 改写句 0.57–0.93；无关句 0.0–0.4。中文里的**取值改变**（"蓝色" -> "绿色"）只有 0.29，因此**无法可靠捕获**——
不同的取值在两端各替换了一个 bigram。测试只断言能工作的情形，并在注释中说明；不去断言不工作的情形。

**放弃了什么。** 措辞不同的矛盾仍无法检出，可能同时被召回。缓解：一旦检出就只保留一条；且冲突以复核建议呈现，而不是自动删除。

**可推翻条件。** 一个基于 embedding 的比较，在同一批配对上能捕获上述取值改变的情形。

## 2026-11-05 —— 取代上一条：对话提炼默认走廉价本地过滤

**决定：** `CLONE_AI_MEMORY_MINING` 现在是三档开关。未设置 = `filtered`：回合里含"持久陈述信号"时
才提炼（`src/memory/mining-policy.ts`）；`off` 同时关闭对话与任务提炼；`all` 每轮都提炼。任务提炼
除非处于 `all`，仍使用确定性 Worker。

**为什么改变上一条。** "显式开启"意味着个人 Agent 最需要的能力——无需被要求也能学习——开箱即关闭。
过滤器在本地运行、不产生模型调用，且宁可多提炼：漏掉一条陈述就是一条永远学不到的记忆，多一次调用只是几分钱。

**放弃了什么。** 没有信号的回合永不被提炼，因此一条陈述得很直白却不含任何匹配模式的记忆可能被漏掉。
`all` 是逃生门。

**可推翻条件。** 若实践中发现过滤器的漏检明显，就扩充信号列表，或把 `all` 设为默认。

## 2026-11-05 — 按 runId 和文件指纹消费已修复轨迹

**决定。** 为每个 runId 保存最近一次成功批次的结果和原始输入文件 SHA-256；只有
两者都匹配时才跳过。仅 `fixed`、`pr-created`、`patch-only` 会消费，错误仍可重试。
使用同目录重命名持久化；文件不可读或格式错误时按空状态处理。

**依据与备选。** 当前 `loadTraces` 没有先前结果记录，会再次送修未变化的轨迹；
这是代码观察，不是生产事故测量。一直重试浪费修复工作，只记 runId 则会漏掉新内容。
完整的模型依赖流程超出本次离线任务，效果仍属**假设**。状态丢失或损坏可能导致重复工作；
成功结果之后的其他步骤失败不会撤销成功记录。

**推翻条件。** 如果需要跨机器共享的持久账本，或轨迹导出经常改变字节但有效证据不变、
因而反复触发修复，就替换这一文件方案。

## 2026-11-05 — Agent 自己运行对抗性测试与修复回路

**决定。** 增加一套确定性、离线的对抗性测试（注入包裹、审批重放/过期/转发、受保护路径与符号链接逃逸、Worker 环境中的工具凭据、secret 记忆召回、轨迹脱敏、限流），并增加一个自检回路：每一轮写入 Journal；探针变红时把失败导出为轨迹，交给既有的带闸门修复通道。每轮运行对抗套件、`npm run gate`，可选 `npm test`；修复仍只产出草稿 PR，合并权在所有者。

**被否决的备选。**（a）以模型驱动的红队为主回路——不确定、每轮消耗 token、跨轮无法比较；留作后续层。（b）让回路直接改代码——违反既有修复闸门，也让"是否变好"无法回答。（c）另起测试运行器——仓库已有 `npm run gate` 与 `node --test`，第二套会漂移。

**证据。** 每个探针都对应代码里已经存在的边界，并有单测或既往事故：转发 WhatsApp 内容（`forwarded` + `<untrusted_data>`）、审批码（一次性、哈希、TTL）、`forbiddenRoots`、`assertWorkerEnvName`、secret 记忆排除、`digestEvents`。套件把这些变成同一个可测量、可记录的信号，而不是散落的假设。确定性探针在本次修订上通过；回路的修复分支用 `--dry-run` 验证。

**成本与推翻条件。** 每轮只耗 CPU，增加一条 Journal 事件和一个报告文件；只有探针变红且传入 `--repair` 时才消耗模型 token。若套件不再能区分回归与噪声（探针无论代码如何都通过），或真实事故暴露了套件未覆盖的类别，应扩展套件而不是放宽它。

## 2026-11-04 — 失败轨迹与修复只在有闸门的草稿 PR 通道运行

**决定。** 失败与取消的 Run 变成脱敏的自包含轨迹，包括没有错误码的隐性失败：同一步骤重试
三次以上、取消、被判“不合格”、或运行结束后十分钟内的所有者纠正。夜间修复在全新 worktree
中运行，要求回归测试在修复前被脚本验证为红，跨阶段对测试文件做哈希，禁止受保护路径进入
diff，只产出草稿 PR（或补丁文件）。它从不合并、部署、重启或修改自己的计划。

**依据。** 无人值守的代码生成是系统里风险最高的动作。每道闸门对应一种已知失效模式：在正在
服务的检出里写代码；没有复现的“修复”；模型靠重写测试让套件变绿；修复改动了审判它的规则；
以及自动合并。`scripts/nightly-rsi.mjs` 实现了全部五道，并在报告里声明合并仍由所有者决定。

**代价。** 测试加 diff 检查只能限定伤害，不能证明修复安全；PR 仍需人读。没有轨迹就不运行，
失败时保留 worktree 供检查。

**推翻条件。** 不要为通用修复放宽草稿 PR 闸门。若沙箱化运行器能对全量测试证明修复并机械
执行受保护路径规则，另一条取舍可以允许对具名路径白名单自动合并——绝不针对宽泛变更。

## 2026-11-04 — 自我评审只改配置，不改规则

**决定。** 评审读取审计摘要，最多提出四个动作，仅限 worker 或主 Agent 的模型与推理强度。
每个动作对照机器声明支持的能力校验，只在所有者点击时应用，以 `recommendation.applied`
记录前后值，并可在同一行撤销。代码、提示词、策略与证据规则不可触及，且不会自行运行。

**依据。** 能自行扩大权限的 Agent 是风险而不是改进回路；权限与完成判定属于 Kernel。摘要
本来就是 Journal 的投影（`loadAudits` / `summarizeAudits`），评审者不需要新数据路径；模型
失败时降级为实测事实（`test/self-review.test.ts`）。

**代价。** 窄接口无法修复代码或提示词缺陷，只能调模型与强度。这是有意的。

**推翻条件。** 若配置接口无法处理某类真实失败，新增动作类型必须单独写取舍并自带校验与
回滚——绝不把这一条扩到代码、提示词、策略或证据规则。

## 2026-11-04 —— 移除哈希 n-gram"语义"召回项

**决定：** 移除。`MdMemoryStore.recall` 保留 bigram 比例、IDF 加权余弦、偏好先验与虚词下限。

**备选：** 保留在 `CLONE_AI_RECALL_SEMANTIC` 开关之后；换成真实 embedding 服务。

**为什么输。** 在 LongMemEval-s（470 道计分题、完整干草堆、maxResults=10）上做消融：

| 指标 | 有语义项 | 无语义项 |
| --- | --- | --- |
| any@1 | 77.9% | 76.6% |
| any@5 | 91.3% | 91.7% |
| any@10 | 95.5% | 94.9% |
| ndcg@10 | 82.0% | 81.5% |
| 上下文命中率 | 92.6% | 92.8% |

差值方向不一致，且在 n=470 时处于噪声范围内。一个无法证明有帮助的排序项，就是每次查询的纯成本
（每个候选多一次 SQL 取数、一张 2048 bucket 的表、约 40 行哈希代码）。

**放弃了什么。** 它本来想覆盖的场景——不共享任何精确词项的改写，例如"周五要交周报了"对
"每周五提交工作汇报"——不再被覆盖。不过在基准上它也从未被证明有效。

**可推翻条件。** 满足任一条：

- 出现真实的 embedding 端点（本地模型或网关能力），并在偏好题切分上胜过词法路径，而偏好题正是
  弱项：any@1 20.0%、any@10 70.0%；
- 出现结构上就不可能有精确词项重叠的产品问题类型（跨语言、大量缩写）；
- 在更大样本（LongMemEval-m）上重跑，差值符号反转。

## 2026-11-04 —— 保留 IDF 加权余弦项

**决定：** 保留在 `recall` 中。

**为什么赢。** 它不会引入任何不共享词项的记忆，最坏情况只是重排已经匹配上的记忆；同一次改动中加入的
虚词下限消除了它真正的失效模式（单个 "the" 就能通过 0.2 比例下限）。

**放弃了什么。** 每次召回、每个候选多一次 SQL 查询。

**可推翻条件。** 值得单独重测；若同样没有收益，按与语义项相同的标准移除。

**状态：** 目前是推测——尚未单独测量。

## 2026-11-04 —— 记忆推入 Main Agent 的 Prompt，而不是只留给拉取

**决定：** 每个回合由 `before_agent_start` 把匹配的记忆重新编译进 System Prompt。

**备选：** 只保留 `recall_memory` 工具路径；改为注入一条 user 角色消息。

**为什么赢。** 只拉不推意味着所有者批准过的记忆仍可能被当作不存在。走 System Prompt 复用了 Worker
已有的 1200 字符 / 6 条边界，且不改动对话历史（注入 user 消息会出现在对话记录与 `readConversation` 中）。

**放弃了什么。** 每回合一次召回（短生命周期 SQLite 句柄）；System Prompt 逐回合变化，削弱 Prompt 缓存。

**可推翻条件。** 若每回合延迟变得明显，或 Prompt 缓存节省的收益压过推送准确度。

## 2026-11-04 —— 对话提炼默认关闭（`CLONE_AI_MEMORY_MINING=1`）

**决定：** 与任务提炼一致，默认关闭。

**为什么赢。** 每个所有者回合一次模型调用。默认开启会把预算花在没产生值得记住内容的对话上。

**放弃了什么。** 开箱即用时，分身不会从对话中学习——这是与陪伴类产品最大的功能差距。

**可推翻条件。** 一旦有廉价或启发式的前置过滤能排除明显不含持久陈述的回合，提炼器即可默认开启。

## 2026-11-04 —— 失败聚类的教训通过 author 写入，而非提炼候选

**决定：** 同一失败签名出现 3 个以上 Run 时，经所有者批准通过 `MemoryGovernance.author()` 写入一条
`procedure` 记忆，而不是作为提炼候选。

**为什么赢。** 提炼候选只能引用自己 Run 的证据；聚类横跨多个 Run，没有单个 Run 能为其作证。所有者的批准
就是证据。

**放弃了什么。** 教训文本是模板拼出来的（类别、次数、签名、目录建议），而不是模型撰写。

**可推翻条件。** 若教训质量比引用纯度更重要，可允许带显式证据集的跨 Run 候选。

## 2026-11-04 —— 原生 Worker 靠环境变量开启，而非默认

**决定：** `CLONE_AI_NATIVE_MODEL` + `CLONE_AI_NATIVE_BASE_URL` 显式开启；否则 Registry 继续使用
沙箱化的 CLI Worker。

**备选：** 作为默认；总是注册但在派发时失败。

**为什么赢。** CLI Worker 有 OS 强制边界；原生 Worker 的边界由我们自己的代码保证。在它积累生产里程之前，
更安全的默认应当是有沙箱的那一个。

**放弃了什么。** 需要理解两种 Worker；原生路径尚未在大规模下验证。

**可推翻条件。** 原生 Worker 跑过真实所有者任务且没有边界回归后，可成为非编码任务的默认。

## 2026-11-04 —— 归档而不是删除

**决定：** 过期、闲置、淘汰都只归档，不销毁。

**为什么赢。** `memory.restored` 使每个决定都可回滚，Journal 也因此诚实地记录了分身曾知道什么。

**放弃了什么。** 原则上磁盘占用无上限。

**可推翻条件。** 增加"归档超过 N 年的记忆清理"，需所有者明确同意并记录原因。

## 2026-11-04 —— 90 天寿命与 90 天闲置

**决定：** 提升的记忆默认 90 天过期；任何活跃记忆 90 天未被使用即归档。

**为什么赢。** 90 天对应一个项目、一个工作周期或一个学期——所有者本人的说法。

**放弃了什么。** 一条仍然为真、只是 90 天内没被召回的事实会从召回中消失。可恢复，但需要所有者注意到。

**可推翻条件。** 若改进环路的使用数据显示被恢复的记忆其实仍有用，就延长窗口或豁免手写记忆。

**状态：** 90 天这个数字来自所有者的描述，是推测值，未测量。

## 2026-11-04 —— 所有者标签高于系统验证

**决定：** 结局归因中以 `audit.labeled` 判定好坏，系统验证作为兜底。

**为什么赢。** 标签是评估用来对照系统的真值。两者不一致时，按定义系统是错的。

**放弃了什么。** 一次草率的标签会污染该 Run 暴露过的每条记忆的归因。

**可推翻条件。** 若标签被证明噪声大，对已完成 Run 的 `fail` 标签要求附注或二次确认。

## 2026-11-04 —— 改进建议是确定性的，且待决上限 10 条

**决定：** 建议 id 由依据推导（`retire:<id>@<bucket>`），同时最多 10 条待决。

**为什么赢。** 每次扫描重算不能产生重复；建议泛滥会训练所有者盲目通过，等于废掉门禁。

**放弃了什么。** 一条真正新的建议可能被推迟到旧建议被决定之后。

**状态：** bucket 大小与上限 10 都是推测值，尚未调参。
